# Helichopter code and release-readiness audit — September 5, 2026

**Verdict: not ready for App Store submission.** The app builds, and its current automated suite passes, but accessibility functionality and validation remain incomplete. Professional testing is necessary; it is not the only work remaining.

## Scope and evidence

Reviewed the Swift source, game state transitions, input routing, settings, scene archives, assets, project configuration, and existing tests. Preserved the pre-existing flight-control edits in PlayingState.swift and HelicopterNode.swift.

- Original suite: 29 tests passed on the iPhone simulator. It missed the defects below.
- Expanded suite: **38 tests passed on each of two simulators** — iPhone 17 Pro and iPad mini (A17 Pro), both iOS 26.5. **76 test executions, zero failures or skips.**
- Tests now exercise bundled scene loading, all 20 helicopter frames, pause/resume before and after first input, retry and saved scores, hidden buttons, hidden scores, settings migration, a stationary background, and scene deallocation.
- Optimized Release build for generic iOS devices: succeeded with signing disabled. No Swift compiler warnings were reported; Xcode emitted an App Intents metadata warning because this game does not use App Intents.
- Verified PrivacyInfo.xcprivacy is present in the built Release app, with the UserDefaults CA92.1 reason and no tracking/data collection declarations.
- Checked asset catalog filename references: none missing.
- Visual simulator inspection was attempted, but UI automation timed out and overlapped with test-runner app launches. **No complete manual gameplay or accessibility session is claimed.**
- No physical-device, performance, accessibility-inspector, signed archive/export, TestFlight, or App Store Connect validation was performed.

These are targeted tests and a source audit, not proof of an absence of bugs.

## Release blockers remaining

### 1. UIKit Settings switch navigation — implemented; hardware validation pending

The follow-up now routes Settings switch input to its visible UIKit controls through the shared FocusScanner. It supports timed one-switch and manual two-switch navigation, Back, toggles, presets, palette scrolling, slider adjustment panels, segmented choices, and the Settings lock. Focus survives panel rebuilds; disabled rows are skipped and outgoing scanners stop.

Automated interaction tests cover these paths, including a timed one-switch adjustment/Back session. Physical keyboard-emulating switches, adaptive controllers, system Switch Control, and VoiceOver still require device validation. System Switch Control and the application's hardware-input scanner are separate paths; the automated tests do not certify the system accessibility experience.

### 2. Gameplay hardware-switch Pause — implemented; hardware validation pending

A primary keyboard/controller switch held for three seconds now pauses gameplay in all four flight schemes. Settings exposes a bounded 2–10 second delay. Shorter holds retain their flight behavior; sustained hover users can increase the delay or release and re-press before it expires. This is a deliberate hold gesture, so switches must provide both press and release events.

The pause menu starts scanning even when automatic menu startup is disabled, and retains the selected one-switch/two-switch scan mode. The player must release the pause gesture before selecting a menu item. Pending holds are cancelled on release, gameplay exit, scene removal, and interruption. Home returns immediately and stops the outgoing scanner, avoiding a transition that can stall from the paused scene. Physical switch/controller usability and system Switch Control validation remain outstanding.

### 3. VoiceOver flight — implemented; sound-only usability validation pending

Implemented September 8: a stable accessibility flight element is attached to the actual UIKit scene overlay. Double-tap handles all four schemes, with toggles for held controls. Custom actions provide downward movement where supported and Pause; accessibility escape also pauses. Switching VoiceOver status pauses and clears held flight controls.

Live values and rate-limited VoiceOver announcements describe altitude, the nearest upcoming pipe, and vertical gap alignment using the player's collision radius. Guidance is spoken at most once every two seconds, independently of game sound effects. This provides functional input and spatial feedback, but does not establish sound-only playability at every speed/difficulty; continuous sonification is not implemented.

### 4. Gameplay contrast boundaries — implemented; low-vision validation pending

**Original finding (September 5):** HelicopterNode.swift:113 replaces the selected palette's helicopter color with the theme override. PaletteContrastTests.swift only compares unmodified helicopter and pipe palette colors. It never checks the theme override or the background texture.

Calculated examples using the source sRGB constants:

| Color pairing | Relative-luminance contrast |
| --- | ---: |
| Parchment red helicopter / Default green pipe | 1.34:1 |
| Parchment red helicopter / High Contrast blue pipe | 1.65:1 |
| Low Luminance pipe / Night Sky solid scene background | 1.21:1 |
| Default pipe / Night Sky solid scene background | 2.61:1 |

The real sky and grayscale art have varying luminance, so these constant-color calculations are diagnostic, not a rendered-pixel audit. The project document's requirement of 4.5:1 on all three pairings is not enforced. This is the project's own design target, not a claim that every game sprite is universally subject to a 4.5:1 text requirement.

Implemented September 7: the helicopter has an opaque black flight marker with black/white borders, and pipes have matching two-tone silhouette borders. Both bands are rendered independently of palette and texture tint. The black/white pair is 21:1; for any single backdrop luminance, at least one band exceeds 4.5:1. This boundary treatment replaces the previous three-way fill-color target, and does not certify every artwork pixel or every textured edge. No-fail feedback now pulses tint instead of fading the entire player. Hitboxes are unchanged; borders are visual guides. Device evaluation with low-vision players remains outstanding.

### 5. Dynamic Type — implemented; device validation pending

**Original finding (September 5):** Settings used fixed fonts, fixed-height controls, and unscaled palette and section labels. SpriteKit text did not support content-size preferences.

Implemented September 7: Settings uses UIFontMetrics and automatic font updates, multiline labels, vertical presets, measured scrollable segments, and larger palette cards. Text-size changes rebuild Settings while preserving scroll/focus and open adjustment panels. A UIKit layer presents scalable title/pause/round-over menus and gameplay text independently of scene scaling. Menu buttons retain the SpriteKit action/scanner model and scroll focused controls into view; gameplay background touches pass through to flight input.

Physical-device, Accessibility Inspector, VoiceOver/Switch Control, and long-localization validation remain required. Automated checks do not certify the complete assistive-technology experience.

## Defects fixed during this review

| Defect | Change |
| --- | --- |
| Background speed 0 was read as 80, so “Still” never stopped it | Distinguish a missing saved value from an explicit zero; reject nonfinite/negative values when reading this setting |
| Resuming reset gravity to off | Apply new-run initialization only on fresh starts/retries; preserve gravity across pause |
| Held controls could remain active through pause | Clear held state and block helicopter touches while paused |
| First-input and pipe-spawn closures retained the game scene | Use weak scene/target captures; regression tests verify scene deallocation before and after starting |
| Pipe cleanup removed the first matching pipe rather than its own node | Each pipe removes itself at the end of its movement |
| Hidden Pause and outgoing overlay buttons entered scanning | Exclude hidden/disabled buttons and detach outgoing overlays synchronously |
| Focus indication relied on animations that cannot run in a paused scene | Apply focus visibility immediately and create an outline when the archive lacks one |
| A scanner could restart a timer after activation stopped it | Check active state after activation, reset on start, invalidate on deallocation |
| Score hiding did not apply on the initial frame | Initialize the HUD from settings and omit the accessibility score when hidden |
| Score contacts could count a threshold multiple times | Mark each threshold as scored and ignore contacts outside PlayingState |
| Game-over speech used the reset score | Capture the final score before the state transition |
| Reduce Motion changes cancelled the invulnerability expiry action | Give rotor animation its own action key; preserve gameplay timers |
| No-fail flashing ignored existing calm/reduced-motion preferences | Suppress the flashing action when either preference is active at collision time |
| Background delta jumped after long pauses; tile count and recycling disagreed | Bound elapsed time and create the intended number of tiles |
| Lock Settings permanently blocked access to its own unlock control | Settings opens with gameplay controls disabled; the lock control remains reachable |
| Applying a preset left the visible controls stale | Rebuild the panel after preset changes, preserving scroll position |
| Settings sliders/toggles lacked direct spoken labels | Add labels/hints, selected palette traits, and modal accessibility behavior |
| Scene update compared delta to an unrelated timestamp | Bound elapsed time correctly |

Settings storage now accepts an injected UserDefaults instance. Settings/scanner tests use their own stores instead of changing the app's preferences. Scanner tests run on the main actor; the timer test no longer fails merely because a three-item scan wrapped to index zero.

Some fixes have direct regression coverage; visual focus, UIKit lock/rebuild behavior, physical contacts, and accessibility behavior still require manual validation. The lock prevents casual changes; it is not an authenticated caregiver gate.

## Other engineering work worth addressing

- **Fixed in the follow-up below:** auto-hover and two-switch damping now use elapsed time. Physical-device testing under load remains open.
- **Fixed in the follow-up below:** scene deactivation and controller disconnection pause active gameplay and clear held input. Physical-device interruption/disconnection validation remains open.
- Most tunable values accept arbitrary values without validation. Pipe geometry assumes sensible, ordered gap bounds. The current UI supplies bounded values, but future profiles/imports should validate them at the model boundary.
- The state machine permits every transition. Constrain transitions as input/navigation grows, and test repeated activation and simultaneous contacts.
- SceneOverlay force-unwraps its archive/template. All bundled files load in this run; keep archive integrity tests when editing these assets.
- Several displayed parameter choices are coupled or omitted, despite the project statement that every tuning parameter is independently adjustable through the app.
- Test deployment target is iOS 26.5, while the app target is **iOS 13.0**. README's iOS 17+ statement was inaccurate. This review exercised only iOS 26.5; oldest-supported OS/device coverage remains open.

## Release preparation

The actual project is version **2.0 (1)**. The privacy manifest is already in the target; older notes saying it still needs to be added are stale. No distribution certificates or App Store Connect account state were inspected.

Apple currently requires iOS uploads to use the iOS 26 SDK or later. The installed Xcode 26.6 meets that minimum generation, but a successful unsigned build does not establish distribution/signing readiness. See [Apple's submission requirements](https://developer.apple.com/app-store/submitting/).

Recommended release gate: resolve the functional accessibility gaps above; run [Accessibility Inspector](https://developer.apple.com/documentation/accessibility/accessibility-inspector); complete physical-device sessions with VoiceOver, system Switch Control, keyboard emulation, and an adaptive controller; check all themes and large text sizes; profile the oldest supported device; then obtain real-user TestFlight feedback. Apple also recommends simulated and real-device testing before distribution: [Distribute an app through the App Store](https://help.apple.com/xcode/mac/current/en.lproj/dev067853c94.html).

Only then finish the signed archive, screenshots, accurate accessibility declarations, listing/privacy information, age rating, and submission.
